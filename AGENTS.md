# DockFleet: repository working agreement

How to work in this repository. The rules are about the repository and the safety of the machine it is built on, not about any one task.

## Boundaries

- Work inside this repository only. Do not read, modify or run commands in other repositories or in user-level configuration.
- Keep every tool, dependency, cache, toolchain, temporary file and piece of test data inside the repository: pinned tools under `.tools/`, local state under `.agent-local/` (both git-ignored), Python packages in `.venv`. Use existing system tools read-only, or install pinned tools under this repository.
- Never install anything globally. Do not use sudo, Homebrew, launchd, host credentials or the host's Docker socket, and do not change shell profiles, user settings, the keychain, global Git settings or operating-system settings.
- Bind test servers to loopback and use ports 21200–21299 only (the allocation is listed under Test coverage). Limit build and test workers to two (`GOFLAGS=-p=2`).
- Docker-dependent tests must stay reproducible, and are reported as unverified when they cannot run where you are working. Never run them against the host's own Docker.
- Choose sensible defaults and document the assumption instead of stopping for small decisions.
- Implement what was asked, keep earlier behavior, run the checks below, fix failures rather than weakening tests, and report real limitations without inventing test or benchmark results.
- Before finishing a piece of work: stop the servers and watchers you started, remove scratch output, update the documentation the change touches, and commit with a conventional-commit message. Do not push unless asked to.
- Report what changed, the checks actually run and their results, what is unverified or limited, and the commit hash.

## Project: DockFleet (Go)

DockFleet is a distributed container orchestration system: a manager (control plane) and agents (worker nodes) communicating over gRPC, with state in PostgreSQL. See `README.md` for usage and `docs/architecture.md` for design. The manager schedules and reconciles services into workloads and sends agents idempotent instructions; agents create, start, stop and remove the Docker containers they are told about (`docs/reconciliation.md`). Update both documents when that changes.

### Layout and dependency direction

- `cmd/manager`, `cmd/agent`: entry points only. Parse config, wire dependencies, handle signals. No business logic.
- `internal/manager` wires `api`, `placement`, `reconcile`, `protocol`, `registry`, `logstream`, `metrics`, `dashboard`, `election`, `etcd` and `store` (`placement` and `reconcile` both use `rollout`; `placement`, `reconcile`, `protocol` and `api` use the `election.Fence` contract); `internal/agent` wires `protocol`, `logstream` and `docker`.
- `internal/api` (admin HTTP), `internal/protocol` (gRPC service, client, versioning), `internal/registry` (manager-side node sessions), `internal/scheduler` (pure placement decisions and explanations: no I/O, no clock, no Docker; `TestSchedulerStaysPure` pins its imports), `internal/placement` (carries decisions out: reads the store, runs the scheduler, saves assignments and explanations), `internal/logstream` (container logs from agents to readers: the manager's hub of the agents' log streams, queries, merging by time, credit-based flow control and resuming; no I/O, standard library only, `TestLogstreamImportsOnlyTheStandardLibrary` pins its imports), `internal/metrics` (a small Prometheus-compatible registry: instruments, collectors read at scrape time, the text format; standard library only, `TestMetricsImportsOnlyTheStandardLibrary` pins its imports), `internal/dashboard` (the server-rendered read-only dashboard; it reads only through the API's handler), `internal/election` (optional high availability: the elector over a `Backend`, and the `Fence` contract; standard library only, `TestElectionImportsOnlyTheStandardLibrary` pins its imports), `internal/etcd` (the election's `Backend`: a client of etcd's JSON gateway on `net/http`, no etcd module), `internal/etcdfake` (an in-memory etcd for tests only), `internal/outage` (when the manager's store last failed, so that silence it could not have heard is not counted; standard library only, `TestOutageImportsOnlyTheStandardLibrary` pins its imports), `internal/healthcheck` (the probe behind each binary's `healthcheck` subcommand), `internal/testnet` (test servers on the project's port range), `internal/e2e` (end-to-end tests, build tag `e2e`, no non-test code), `internal/rollout` (the pure rules of a rolling deployment: readiness, how many replicas may be created and retired under a service's `max_surge` and `max_unavailable`, what a rollout waits for, and the state machine of its record; `TestRolloutStaysPure` pins its imports), `internal/reconcile` (stops, and deletes, the workloads that should go, including those of a node that was given up on, and records node health: a pure `Plan` plus its application with audit events), `internal/store` (persistence), `internal/docker` (agent-only Docker Engine adapter), `internal/dockerfake` (in-memory `docker.Runtime` for tests only), `internal/netutil`, `internal/pki` (certificates, node identity, TLS configs; imports nothing from the other internal packages), `internal/config`, `internal/logging`. `cmd/pki` is the certificate CLI. `internal/integration` is tests only; `internal/pgtest` is a test helper that makes throwaway PostgreSQL databases and depends on nothing else here.
- The services REST API (`/v1/services`, `docs/api.md`) only records desired state: its handlers must not schedule or write nodes or workloads (they may read workloads and the scheduler's explanations to show a service's `status`). Scheduling is `internal/placement`'s job, not a request handler's. A new definition field needs an entry in the allow-lists in `internal/api/services_validate.go`, validation with a limit at least as strict as the agent's policy in `internal/docker/policy.go` (the manager cannot import it), canonicalization so equivalent definitions hash alike, and tests in the `internal/api/services_*_test.go` suite, which must keep passing against both the in-memory store and PostgreSQL.
- Scheduling rules (`docs/scheduler.md`) change only together with that document and table-driven tests in `internal/scheduler`; decisions must stay deterministic (same snapshot, same answer, whatever the input order) and every refusal needs a reason. Nothing is oversubscribed unless `DOCKFLEET_SCHEDULER_*_OVERCOMMIT` says so.
- Reconciliation (`docs/reconciliation.md`) keeps these properties, each pinned by tests: instructions are states the agent converges to from a fresh look at its containers, never one-shot commands; a workload ID is random, never reused and names at most one container; a workload only goes running, then stopped, then deleted, and is deleted only after its node acknowledged the stop and reported no container; the agent only acts on containers carrying its DockFleet labels, does nothing before the manager has answered once, and removes unassigned managed containers only after a grace period. A change to any of them updates that document and the tests in `internal/reconcile`, `internal/agent` and `internal/integration`.
- Scaling (`docs/api.md#scaling`, `docs/reconciliation.md#scaling`) keeps these properties, each pinned by tests: a service wants a number of replicas, not particular ones; the scale endpoint only records the count and is idempotent (the count it already has changes nothing, not even with a stale `If-Match`); the scheduler creates only the replicas a service lacks, in the lowest free slots, and never oversubscribes to satisfy a count; the reconciler chooses the replicas to stop by how little good they do, then by node balance, deterministically from stored state, and a replica that stays is never restarted, replaced or given a new generation. A change to any of them updates those documents and the tests in `internal/reconcile`, `internal/placement`, `internal/api` and `internal/integration/scale_test.go`.
- Failure handling (`docs/failure-handling.md`) keeps these properties, each pinned by tests: a node's state comes only from how long it has been silent (`scheduler.Timing`, one implementation for the reconciler, the scheduler and the API); silence from before the manager started is never counted; a node is given up on only after the lease the agent fences itself by plus a heartbeat (`DOCKFLEET_NODE_UNAVAILABLE_AFTER` is validated against `DOCKFLEET_NODE_LEASE`); an agent counts its lease from when it sent the heartbeat; moving a replica stops the old workload (generation up) and creates a new one with a new ID, never edits or restarts it, so a returning node is always told to remove what it no longer owns; standalone workloads are never moved; restart waits and limits live in the restart policy and the agent, not in the manager. A change to any of them updates that document and the tests in `internal/reconcile`, `internal/agent` and `internal/integration/failure_test.go`.
- Rolling deployments (`docs/rollouts.md`) keep these properties, each pinned by tests: a rollout never has more replicas meant to run than the wanted count plus `max_surge`, nor fewer ready than the wanted count minus `max_unavailable` (the scheduler pass creates and the reconciler retires from the same `internal/rollout` numbers, so two managers agree); a replica is ready only when its agent acknowledged the latest instruction, reports it running and, if it has a health check, the check passes; when a rollout cannot move without breaking either limit it waits and says why (nothing is retired to make room unless `max_unavailable` allows), and after `progress_deadline_seconds` without progress it is reported failed but carried on; pausing stops both creating and retiring and stops the deadline; a rollback deploys an old spec as a new revision and keeps the replicas that already run that spec (`Definition.SameSpec`); `pause`, `resume` and a rollback that names its revision are idempotent; the rollout record is derived state written only by the reconciler. A change to any of them updates `docs/rollouts.md` and the tests in `internal/rollout`, `internal/reconcile`, `internal/placement`, `internal/api` and `internal/integration/rollout_test.go`.
- Container logs (`docs/logs.md`) keep these properties, each pinned by tests: the manager never connects to agents, so the agent opens one `Logs` stream per session and serves the requests that arrive on it; that stream is authenticated like every agent call, bound to the node's current session and enrollment (rechecked while it is open) and, under mutual TLS, to the certificate identity; everything an agent sends is validated before the hub sees it, and the hub accepts lines only for requests it opened on that very stream; memory is bounded at every stage by credit: an agent sends only the bytes it was granted, the hub returns credit only as the reader takes lines out, a line is cut at a limit without being buffered whole, and a response whose client takes no data for the write timeout is closed; a query that follows resumes after the last line it delivered when an agent's stream drops and returns, so nothing repeats and nothing in Docker's log is skipped; the agent reads only containers that carry its own node's DockFleet labels; the log endpoints only read, need the admin token, and never write log contents to the manager's own log. A change to any of them updates `docs/logs.md` and the tests in `internal/logstream`, `internal/agent`, `internal/protocol`, `internal/api` and `internal/integration/logs_test.go`.
- Observability (`docs/observability.md`) keeps these properties, each pinned by tests: `/metrics` and `/dashboard` need the admin token and change nothing; the fleet's gauges are computed from the store on every scrape with the code that answers the API (a metric never holds a copy that can drift), and the counters and histograms are fed by the code that does the work, through `Observer`/`Observe` hooks, so `placement`, `reconcile` and `protocol` never import a metrics library; label values are bounded (route patterns, not paths; unknown methods are `OTHER`; at most 1000 series per instrument); a failed pass counts as an error and its decisions are not counted, a pass cut short by shutdown counts as nothing, and a rollout failure is counted once and only after it is saved; the dashboard calls the API's handler in process and renders its JSON (it has no store access, no `POST` but login and logout, no script, and escapes everything the cluster reports); its session is a signed expiring cookie that holds no secret, and a login is rate-limited, cross-site-proof and returns only to `/dashboard`; every request that can change something leaves one `audit` log record with the outcome (denied and rejected attempts included), and every audited event carries the same `request_id` and the `remote` address of the connection, never a forwarding header; request bodies, queries, credentials and environment values are never logged. A change to any of them updates `docs/observability.md` and the tests in `internal/metrics`, `internal/api`, `internal/dashboard`, `internal/placement`, `internal/reconcile` and `internal/manager`.
- High availability (`docs/high-availability.md`) keeps these properties, each pinned by tests: it is optional, and a manager without `DOCKFLEET_ETCD_ENDPOINTS` checks no epoch and runs no election, exactly as before; etcd holds the election and nothing else, and every epoch comes from the database (`control_plane`, `BeginTerm`), never from etcd; every pass of the scheduler and the reconciler and every `POST /v1/workloads` takes the placement lock and then `CheckEpoch`s its epoch inside the same transaction (`FOR SHARE` against `BeginTerm`'s `FOR UPDATE`, so a term cannot begin while such a transaction is open), and a refusal because the manager does not lead is not counted as a failure; a manager stops answering agents and starting passes by its own clock at 80 % of the last lease etcd confirmed, counted from before the renewal was sent, and its duties have returned before it is a follower again; a follower issues no instruction (`NOT_LEADER`), and an answer prepared in one term is not sent in the next; an agent obeys no epoch lower than the highest it has heard; node health after a failover is counted from the start of the term (`control_plane.elected_at`), in the leader's loops and in the API alike; etcd is reached with mutual TLS or on loopback, and `DOCKFLEET_NODE_LEASE` must fit a failover (`2 × DOCKFLEET_ELECTION_TTL + DOCKFLEET_HEARTBEAT_INTERVAL`). A change to any of them updates `docs/high-availability.md` and the tests in `internal/election`, `internal/etcd`, `internal/store`, `internal/placement`, `internal/reconcile`, `internal/protocol`, `internal/api` and `internal/integration/ha_test.go` and `ha_stale_test.go`.
- Deployment (`docs/deployment.md`, `docs/credentials.md`) keeps these properties, each pinned by tests in `deploy/artifacts_test.go`, `internal/config`, `cmd/agent` and `internal/e2e`: credentials are files (`DOCKFLEET_*_FILE`), never required in the environment, and a process refuses both forms at once; the images hold one static binary, run as a numeric non-root user, take their health from the binary's own `healthcheck` subcommand and bake no credential; the `Dockerfile` pins (generators, Go release) equal the `Makefile`'s and `go.mod`'s; the examples load through the real configuration code; no file under `deploy/` hands the Docker socket to a service (only the agent's own unit and settings may name it, `TestDeploymentFilesNeverMountTheDockerSocket`), so there is no Compose file for the agent; `-tags e2efake` (an agent with its containers in memory) exists for the end-to-end tests and is in no release build (`cmd/agent/main_test.go`); the health endpoints are read-only and the agent's is loopback-only; `go.mod` names the exact Go release the binaries need (it carries the standard-library security fixes), and `make vuln` (`scripts/vuln-check.sh`) fails on any reachable known vulnerability except the ones listed in that script with a reason. A change to any of them updates `docs/deployment.md`, `docs/credentials.md` or `docs/security-audit.md` as it concerns, and those tests.
- Silence is never held against a node when the manager could not have heard it: not from before the manager started, not from before the current leader's term, and not from before the manager's store last failed (`scheduler.Timing.Outages`, marked by every failed pass and readiness check). An agent never obeys an assignment whose generation is lower than the one it acts on (`runner.Assign`). Tests: `internal/scheduler`, `internal/reconcile` (with a control run), `internal/agent`, and `TestDatabaseOutage` in `internal/e2e`.
- Lower layers (`store`, `scheduler`, `placement`, `reconcile`, `rollout`, `logstream`, `metrics`, `election`, `outage`, `registry`, `config`, `logging`, `netutil`, `pki`) must not import `api`, `protocol`, `manager` or `agent`. Depend on small interfaces (`store.Store`, `registry.Store`, `protocol.Registry`, `agent.Manager`, `docker.Client`) so each package is testable with fakes.
- Docker is agent-only: nothing the manager is built from (`cmd/manager`, `manager`, `api`, `registry`, `store`, `scheduler`, `placement`, `reconcile`, `rollout`, `logstream`, `metrics`, `dashboard`, `election`, `etcd`, `protocol`, and therefore `config`) may import `internal/docker` or a `github.com/docker/...` package (`TestManagerSideNeverImportsDocker` enforces it), and the Docker SDK stays inside `internal/docker/sdk.go`. The adapter only acts on containers carrying this node's DockFleet labels, addressed by workload ID, and rejects privileged mode, Docker-socket and system-path mounts and other dangerous settings by default (`docs/docker.md`); relaxing the policy needs an explicit setting and must keep the always-denied sets.
- Authentication changes (mutual TLS, identity, enrollment) update `docs/mtls.md` and `docs/protocol.md` and get tests in `internal/pki`, `internal/protocol` and `internal/integration` for the failure cases (untrusted, wrong identity, expired, not enrolled, no plaintext fallback), not only the happy path.
- The wire protocol is `proto/dockfleet/v1/fleet.proto` and `docs/protocol.md`. Any protocol change updates both, follows the versioning rules there, and is exercised in `internal/integration`.
- Generated protobuf code lives in `internal/protocol/dockfleet/` and is git-ignored. Edit `proto/`, then run `make proto`. Never hand-edit generated files.

### Scoped changes

- Implement only what the current task asks for. No drive-by refactors, renames, formatting sweeps or dependency upgrades.
- Every changed line should trace to the request. Keep commits to one logical change using conventional commit messages (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `ci:`, `refactor:`).
- New third-party dependencies need a reason in the commit message; prefer the standard library. Pin tool versions in the `Makefile`.
- Database changes are new numbered files in `internal/store/migrations/` (`NNN_description.sql`, no gaps); never edit a released migration (checksums are recorded and `TestReleasedMigrationsAreUnchanged` pins them). Add new migrations to the list in `docs/state.md`.
- Keep desired state (what an administrator asked for) and observed state (what agents reported) apart: separate tables, separate writers, separate fields. Observations are written only through `RecordObservations`; intent is never derived from a report. Anything that must be consistent across several writes goes in one `InTx`; placement takes `Tx.LockPlacement`; concurrent edits of a service use its version (`ErrVersionConflict`). Nothing may keep cluster state only in process memory, because several managers may share the database.
- Public behavior changes (API routes, env vars, RPCs, schema) update `README.md` and `docs/architecture.md` in the same change.
- `docs/verification.md` is the one place that says what is implemented, verified, partial and unverified. Change a row only with the command and the result that justify it, and never write "verified" for something that did not run. `ROADMAP.md` lists the known gaps in priority order; take a step out only when its acceptance criteria are met. `deploy/roadmap_test.go` and `deploy/docs_test.go` keep the roadmap's arithmetic and every relative link and anchor in the documents honest.

### Test coverage

- Every new package or behavior ships with tests in the same change; bug fixes include a regression test that fails without the fix.
- Test through interfaces with fakes. Use `bufconn` for gRPC and `httptest` recorders or fake `http.RoundTripper`s for HTTP and Docker; open a real socket only when the test is about the socket, and then only on `127.0.0.1` in ports 21200–21299 (currently 21288–21295 and 21298–21299 in `internal/manager`; 21240–21259 for the servers tests start with `internal/testnet` (also `etcdfake.Listen`); 21260–21269 for the managers of the multi-manager tests in `internal/integration` (two ports each), which otherwise use an in-memory transport; 21270–21279 for `internal/e2e` (managers 21270–21273, agent health endpoints 21274–21276, a cuttable proxy 21277, etcd 21278–21279) and 21236 for the PostgreSQL it starts, 21279 for one refusal test; 21234 for `make etcd-test-up`). Use `t.TempDir()` for files.
- Tests must not need Docker, a database or the internet. PostgreSQL tests are tagged `integration` and read `DOCKFLEET_TEST_DATABASE_URL` (a server whose role may `CREATE DATABASE`; every test makes and drops its own database and never writes to the one in the URL); Docker daemon tests are tagged `dockerintegration` and read `DOCKFLEET_TEST_DOCKER_HOST` (never against the host's own Docker; `make docker-test-up` starts a disposable daemon); both stores must keep passing `runStoreConformance`.
- Tests must be deterministic: no fixed sleeps as synchronization (poll with a deadline), injected clocks where time matters, and `-race` clean.
- Cover failure paths (bad input, auth failure, dependency errors, cancellation), not only success.

### Clean process management

- Every goroutine has an owner and a stop condition tied to a `context.Context`, a closed channel or a `WaitGroup`. No goroutine may outlive the function that started it unless it is documented.
- Pass `context.Context` as the first parameter of anything that blocks or does I/O; never store contexts in structs.
- Shutdown must be graceful and bounded by `DOCKFLEET_SHUTDOWN_TIMEOUT`, then forced. A requested shutdown exits 0.
- Before finishing a task, stop every server, watcher and container you started (`make compose-down`), and delete scratch files, logs and build output (`make clean`). Report anything intentionally left running.

### Secure defaults

- Bind to loopback by default; a non-loopback bind requires TLS, and TLS on the agent listener means mutual TLS with a verified, identity-bound, enrolled client. Never add a plaintext fallback or a TLS mode without client certificates. Tokens are never defaulted, logged, echoed in errors or committed. The only credentials in the repository are the labeled throwaway tokens in `config/dev.env`.
- Private keys and certificates for development live in the git-ignored `.dev-pki/` (`make dev-pki`), are written owner-only and are never printed, logged or committed; `make check-secrets` (part of `make check`) must pass. Test keys are generated in memory or `t.TempDir()`.
- Validate all external input (HTTP, gRPC, env, files) at the boundary and bound its size. Compare secrets in constant time. Use parameterized SQL only.
- Never expose the Docker Engine API over non-loopback TCP. Do not mount or use the host's Docker socket from development or test code; use the disposable daemon. Docker-dependent steps that cannot run are reported as unverified.
- Do not log secrets, tokens, database URLs or request bodies.

### Verification commands

Run from the repository root with the Go release `go.mod` names (1.26.10 or newer on the 1.26 line), installed under this repository (for example in `.tools/` or `.agent-local/`).

```sh
make generate           # pinned buf + protoc plugins into .tools/bin, lint, generate code (needs network once)
make proto-lint proto   # lint and generate protobuf code with the tools already installed
make tidy               # go mod tidy; writes go.sum (needs network)
make check              # gofmt check, go vet, secret scan, go test -race ./...
make build              # bin/dockfleet-manager, bin/dockfleet-agent
make test-integration   # PostgreSQL store, API, scheduling, reconciliation and multi-manager tests (each test gets its own throwaway database); needs `make compose-up`
make test-docker        # Docker Engine tests: adapter and a service deployment (build tag dockerintegration); needs DOCKFLEET_TEST_DOCKER_HOST
make docker-test-up     # a disposable Docker daemon on 127.0.0.1:21297 for those tests; make docker-test-down removes it
make test-etcd          # the election client and the managers' election against a real etcd; needs DOCKFLEET_TEST_ETCD_ENDPOINTS (`make etcd-test-up` starts a disposable etcd on 127.0.0.1:21234; make etcd-test-down removes it)
make test-e2e           # the real binaries over mutual TLS with PostgreSQL and etcd, failures injected (build tag e2e); starts its own PostgreSQL and etcd from .tools/ or DOCKFLEET_E2E_POSTGRES_BIN / DOCKFLEET_E2E_ETCD_BIN, or uses DOCKFLEET_TEST_DATABASE_URL / DOCKFLEET_TEST_ETCD_ENDPOINTS
make tidy-check cross-build   # go.mod/go.sum are tidy; the released platforms compile
make docker-build       # the manager and agent images (needs a Docker daemon)
make vuln               # govulncheck through scripts/vuln-check.sh (needs network)
```

The toolchain is project-local and git-ignored: `.tools/go` (Go 1.26.10 from go.dev, checksum-verified), `.tools/bin` (the pinned `buf` and protoc plugins from `make tools`, and `govulncheck`). Put `.tools/go/bin` and `.tools/bin` on `PATH` and set `GOTOOLCHAIN=local` so that nothing downloads another toolchain. `go.sum` is committed. A PostgreSQL 16 and an etcd 3.5 binary, if present under `.tools/postgres` and `.tools/etcd`, can serve `DOCKFLEET_TEST_DATABASE_URL` and `DOCKFLEET_TEST_ETCD_ENDPOINTS` without Docker (loopback, a data directory under `.agent-local/data`, removed afterwards).

At most two build/test workers (`GOFLAGS=-p=2`).

### Verification reporting

- Report only checks you actually ran, with the command and its real result (pass/fail, counts). Never paste or invent output you did not see.
- State what could not be run and why (no toolchain, no network, no Docker daemon, no Linux host) and mark those items **unverified**. A change is not "tested" if its tests did not execute.
- Report failures you could not fix, flaky tests, skipped tests and known gaps instead of weakening tests to pass.
- A report ends with: summary of changes, checks run and results, unverified items and limitations, commit hash.
