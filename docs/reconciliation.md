# Reconciliation

DockFleet runs services by comparing what administrators asked for with what agents report, and sending each agent the instructions that close the gap. This document is the whole loop: who decides what, what an instruction looks like, and why repeating, losing or replaying any step is safe.

```
 admin ---> service definitions (desired: replicas, revision)
                 |
                 |  internal/placement   places replicas that have no workload
                 |  internal/reconcile   stops replicas that should go, deletes the ones
                 v                       the node confirmed are gone
          workloads (desired: node, running|stopped, generation)
                 |
                 |  Heartbeat response: the node's complete assignment set
                 v
          agent runner (internal/agent)  creates, starts, stops, removes containers
                 |                       through internal/docker, on this node only
                 |  Heartbeat request: a status for every workload, with the
                 v  acknowledged generation
          observations (observed: phase, container, exit code, restarts, ack)
                 ^
                 +---- read back by the reconciler and shown by the API
```

Every box is stateless between passes: whatever a pass needs, it reads from the store (manager) or from the Docker daemon and the latest assignments (agent). A pass can be repeated, interrupted or run on another manager without harm.

## Workload identity

A **workload** is one container's lifetime on one node. Its ID is 128 random bits (`store.NewID`), generated by the manager that places it, unique in the fleet and never reused: a replica slot that is filled again after its workload was deleted gets a new workload with a new ID, and a container is never started again for a workload that was stopped. The ID is

- the primary key of the workload record;
- part of its name (`<service>-r<revision>-<replica>-<6 hex>`);
- the container's name on the node (`dockfleet-<id>`) and its `io.dockfleet.workload-id` label, which is the only way the agent addresses a container.

So "one workload, at most one container" holds by construction: creating a second container for an ID is refused by the adapter (`ErrConflict`), and by the database the pair (service, revision, replica) can only be held by one workload at a time.

## Instructions: assignments

The manager answers every registration and heartbeat with the node's **complete** set of workloads, each as a `WorkloadAssignment` ([protocol.md](protocol.md)):

| Field | Meaning |
| ----- | ------- |
| `workload_id`, `name` | Identity (above) |
| `image`, `command`, `env`, `ports`, `cpu_millis`, `memory_bytes`, `restart_policy` | How to run the container; copied from the service revision when the workload was placed, so an assignment never changes under its container |
| `desired_state` | `RUNNING`: have a container, running. `STOPPED`: stop it and remove it |
| `generation` | 1 when the workload is created, +1 whenever its desired state changes |

An instruction is a statement of the state to reach, not an action to perform once. That is what makes it idempotent: receiving it twice, late, or after a restart, leads to the same containers.

### Acknowledgments

Every `WorkloadStatus` the agent sends carries `acknowledged_generation`, the highest generation of the workload's assignment it has received. The manager stores it with the observation and never lets it go back. Until a status acknowledges generation *g*, nothing it says is about instruction *g*. The reconciler uses this: it does not delete a stopped workload on the strength of a report that predates the stop, and it does not treat a new replica as up until its agent has seen the latest instruction. The API shows `generation` and `acknowledged` for every replica.

## What the agent does

The **runner** (`internal/agent/runner.go`) runs beside the heartbeat loop, so a slow image pull never delays a heartbeat. Each heartbeat response is handed to it (`Assign`), which wakes a pass; it also passes every 2 seconds, which is how a container that died is noticed. A pass lists the managed containers of this node, then for every assignment, in workload ID order:

| Assignment | Container | What happens |
| ---------- | --------- | ------------ |
| running | none | Create it (pulling the image first if the node lacks it), then start it |
| running | created, never started | Start it (an agent that stopped between create and start) |
| running | running | Nothing; report `RUNNING` |
| running | exited | Apply the restart policy (below) or report `SUCCEEDED` / `FAILED` |
| running | dead | Remove it; the next pass creates a new one |
| stopped | running | Stop it (10 s grace), then remove it |
| stopped | exited | Remove it |
| stopped | none | Nothing; report `STOPPED` with no container |

Every step is taken from what a fresh listing shows, never from what the previous pass intended, so the passes can be repeated indefinitely: `TestRepeatedPassesNeverCreateDuplicates` runs ten passes over the same assignments and finds one `create` per workload.

**Restart policy.** `always` restarts an exited container; `on-failure` restarts it when it exited non-zero or was OOM-killed, at most `max_retries` times (default 5); `no` never does. The first restart is immediate; successive ones wait 1 s, 2 s, 4 s and so on up to a minute, so a crash loop does not spin. The count of restarts is kept in the agent's memory: an agent that restarts counts again from zero.

**Failures.** A failed create, pull, start or policy rejection is reported `FAILED` with the reason, and retried with the same backoff. Nothing is retried in a tight loop and nothing is given up for good: fixing the cause (the registry, the daemon, the spec) is enough.

**Reports.** For every assignment the agent reports phase (`PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `STOPPED`), a short message, the container ID (empty when there is none), the exit code, whether the kernel killed it for memory, its restart count and the acknowledged generation. Messages contain no timestamps or counters that change, so a steady state sends an identical report every time and the manager writes nothing.

### What the agent never touches

- **Containers that are not DockFleet's.** The adapter only sees containers that carry `io.dockfleet.managed=true` and this node's ID, addresses them by workload ID, and re-checks the labels on everything the daemon returns ([docker.md](docker.md)). A container with any other labels, another node's managed container, or a container that squats on the name `dockfleet-<id>` is invisible; creating over such a name fails and leaves it alone.
- **Anything before the manager has answered.** The runner does nothing until the first `Assign`. An agent that has just started, or cannot reach its manager, keeps the containers it finds.
- **Managed containers the manager no longer lists** (orphans) are removed only after they have gone unassigned for 2 minutes. A response that omits a workload for one heartbeat, or a manager that came up with an empty database, does not cost a running service. In normal operation there are no orphans: a workload leaves the manager's list only after its container is gone.

Stopping the agent does not stop containers. They keep running, and the next agent finds them.

## What the manager does

The **reconciler** (`internal/reconcile`) runs every `DOCKFLEET_RECONCILE_INTERVAL` (default 5 s) in one transaction under the placement lock, so it never interleaves with a scheduling pass. `Plan` is a pure function of the services, the workloads with their observations, and the scheduler's explanations:

1. **Scale down.** A workload whose replica index is above its service's replica count is told to stop. So is every workload of a deleted service, whatever its revision.
2. **Rollout.** A workload of an older revision is told to stop once the same replica of the *current* revision is up: its agent has acknowledged the latest instruction and reports it running (or finished successfully). Replicas are replaced one by one and there is never a replica without a running container; if the new one never starts, the old one stays and `status` says why.
3. **Fixed host ports.** If the new replica cannot be placed because the old one holds a fixed host port that the new one needs as well (a host port allows one container per node), the old one is stopped to free it. This is the one case with a gap.
4. **Removal.** A stopped workload is deleted when its node has confirmed that the container is gone: a report made after it received the stop, phase `STOPPED`, no container. Deleting frees the replica slot, and the scheduler fills it with a new workload if the service still wants a replica there.

Stopping is `SetWorkloadDesiredState(stopped)`, which bumps the generation; a workload that is already stopped is skipped (`ErrUnchanged`). Deleting a workload that is already gone is skipped too. A pass either applies its changes and records an audit event for each (`replica.stopped`, `replica.removed`, actor `reconciler`) or, if anything fails, none.

Workloads that belong to no service (`POST /v1/workloads`) are never stopped or deleted by the reconciler.

## Recovery

| What restarts or fails | What happens |
| ---------------------- | ------------ |
| **A manager restarts** | Sessions are lost; each agent's next heartbeat gets `NOT_REGISTERED`, so it registers again and receives its complete assignment set. Workloads, generations and observations are in the database. The agents' runners never stopped, so nothing happens to the containers. |
| **Several managers** | Scheduling and reconciliation passes take the same advisory lock, so they take turns; each sees the previous one's work. |
| **An agent restarts** | It registers, receives the assignments, lists the containers and adopts the ones that match: no container is created for a workload that has one. A container that crashed meanwhile is restarted per its policy; a stop that arrived meanwhile is carried out. |
| **A node is away during a removal** | The manager keeps the stopped workload and its record until the node confirms. When the node returns, its agent removes the container and the record goes. |
| **Docker is unreachable** | The pass changes nothing and is retried; the last reports stay. |
| **A heartbeat or a response is lost** | Both sides send the complete state every time, so the next one repairs it. |
| **The database is rolled back to an older state** | Agents see a smaller assignment set; containers of workloads that vanished are removed after the grace period. |

A node that goes quiet is a different case from any of these: after a suspect period the manager gives up on it and starts its replicas on other nodes, using a lease on the agent's side and the workloads' generations so that the old copy is stopped first or told to go when the node returns. That is [failure-handling.md](failure-handling.md).

## See it work

- `GET /v1/services/{name}`: `status` lists every replica with its node, `desired_state`, `generation`, `acknowledged`, `phase`, message and container, and the count of running replicas.
- `GET /v1/workloads`: the assignments and the agents' observations, side by side.
- `GET /v1/events`: `replica.scheduled`, `replica.stopped` and `replica.removed` with their reason.
- Agent logs: `workload assigned`, `workload status` (when a report changes), `pulling image`, orphan warnings.

## Settings

| Variable | Used by | Default | Meaning |
| -------- | ------- | ------- | ------- |
| `DOCKFLEET_RECONCILE_INTERVAL` | manager | `5s` | Time between reconciliation passes |
| `DOCKFLEET_SCHEDULER_INTERVAL` | manager | `5s` | Time between scheduling passes |

The agent's timings (resync 2 s, orphan grace 2 min, stop grace 10 s, restart backoff 1 s to 1 min, pull limit 10 min) are fixed in `internal/agent`.

## Tests

- `internal/reconcile`: `Plan` as a table (scale down, deleted services, rollouts, failed rollouts, stale reports, port handover, ordering), then the whole control loop on the in-memory store (and PostgreSQL under the `integration` tag, with two managers at once): deploy, repeat passes, scale down, scale up with new IDs, roll out with the invariant that every replica always runs, delete.
- `internal/agent`: the runner against an in-memory Docker engine that behaves like the adapter: creation, adoption after restart, stopping and removal, bystanders, orphans and the grace period, image pulls, backoff, restart policies, policy rejections, unreachable Docker.
- `internal/integration`: real agents and a real manager over gRPC, with the control loops: a service deployed, a manager restart, a crashed container found by a restarted agent, scale down, rollout and deletion with exact counts of creates and removes; a removal that waits for an absent node; retried failures.
- `internal/integration/docker_test.go` (tag `dockerintegration`): the same flow against a real Docker daemon, with another node's container as bystander. **It is not run by `make test`.** Run it against a disposable daemon: `make docker-test-up`, then `DOCKFLEET_TEST_DOCKER_HOST=tcp://127.0.0.1:21297 make test-docker`, then `make docker-test-down`.

## Limitations

- A node that is gone for good keeps its stopped workloads on record, and a replica whose container failed beyond its restart limit is not moved ([failure-handling.md](failure-handling.md#limitations)).
- One container per workload.
- The scheduler counts a workload as freed as soon as it is told to stop, so for a few seconds a node can carry the old container beside the new one.
- Environment values travel in assignments; a node's assignment set is limited to 32 MiB.
- The runner handles workloads one after another: a long image pull delays the others' status updates (not heartbeats).
- Stopping a workload removes its container and with it its logs.
- Restart counts and backoff are kept in the agent's memory.
